# 0.3.10 — menu, state toggles and internal-detector cleanup

**Status:** implemented, post-RC UI/feature release.
**Date:** 2026-11-21.

## Summary

0.3.10 tightens the UI and the detector catalog:

* navigation categories are the same size as links, blue, and collapsible;
* the detector scope split is removed — every remaining detector is external;
  the internal detectors DET-22/24/25 are retired;
* Detectors and Disposition rules use a single green/red state button instead of
  a state label plus a separate action;
* the honeypot fires after 3 contacts and has a shipped Disposition rule that
  blocks through the ladder.

## Navigation

`nav_group()` now renders a native `<details>` element:

```html
<details class="nav-group" open>
  <summary class="nav-head">Monitoring</summary>
  <div class="nav-links">…</div>
</details>
```

* Category headings use the same 15 px size as nav links and the accent
  (blue) color.
* The default disclosure marker is replaced by a small chevron that rotates
  when the group is closed.
* `app.js` persists each group's open/closed state in
  `localStorage` (`rustips-nav-<label>`). The group containing the current page
  always starts open so the active link is not hidden.
* On narrow screens the links wrap inside each group; headings stay on their
  own line.

## Detector scope removed; internal detectors retired

The external/internal split was not useful for the single-host deployment, so
it is gone:

* `DetectorScope`, `Detector::scope()`, the Scope column, counts and filter are
  removed from the model and UI.
* DET-22 (**sudo denial**), DET-24 (**system security change**) and DET-25
  (**account modification**) are removed from `Detector::ALL`. They are no
  longer shown, tuned or emitted by the log engine.
* The variants and IDs are retained only so historical detections, blocks and
  stored rules still decode. `Detector::from_id()` accepts the retired IDs;
  they are not offered when creating new rules.
* `logs.detection.sudo_failures`, `detect_security_changes` and
  `detect_account_changes` remain accepted in configuration and stored
  overrides for upgrade compatibility, but they no longer drive a detector.

The remaining catalog is 21 detectors: DET-01…17, DET-20, DET-21, DET-23 and
DET-26.

## Single-button state toggles

Both Detectors and Disposition rules now show one state button:

* green **Enabled**
* red **Disabled**

Clicking the button flips the state. Detector toggles still use
`POST /detectors/toggle`; rule toggles use the new `POST /rules/toggle`.

* The rule toggle loads the stored rule, flips `enabled`, saves it through
  `Db::save_rule()` and appends a revision, so the existing last-enabled-rule
  protection applies.
* A rejected change (for example, disabling the final enabled rule) redirects
  with a clear notice.
* Both actions are audited (`detector.enable`/`detector.disable`,
  `rules.enable`/`rules.disable`).
* CSS classes `state-on`/`state-off` provide the green/red pill.

## Honeypot threshold and default rule

DET-26 now counts contacts:

* new `detection.honeypot_hits` field, default **3**, editable in Settings;
* a TCP SYN or UDP datagram to a configured honeypot port increments the
  source's contact counter in the shared detection window;
* DET-26 fires when the counter reaches the threshold, and the detection's
  `count` is the number of contacts seen.

New shipped Disposition rule:

| Field | Value |
|---|---|
| Name | Honeypot block after 3 contacts |
| Detector | DET-26 |
| Minimum count | 3 |
| Action | Escalate (configured ladder, first step 1h) |
| Priority | 250 |

The generic packet rule explicitly excludes DET-26, so a honeypot source is
alert-only below 3 contacts and blocked at the threshold. DET-26 is therefore no
longer `is_alert_only`.

### Existing databases

The schema moves from v7 to v9. The migrations are data-only:

* v8 calls `Db::ensure_honeypot_rule()`, which adds the honeypot rule unless an
  operator already has a rule referencing DET-26;
* v9 calls `Db::strip_retired_detectors()`, which removes DET-22/24/25 from
  stored rule match lists. A rule whose only detectors were retired is left
  untouched so it cannot become a catch-all.

Fresh installs get the honeypot rule from `default_rule_documents()` and never
see the retired IDs.

## Known limitations

1. Retired detector IDs remain decodable for history but are not selectable for
   new rules.
2. The contact threshold uses the shared detection window (`detection.window_secs`).
3. The default honeypot rule blocks at **3**; changing the contact threshold
   lower than 3 should be paired with a custom rule if immediate blocking is
   required.
4. Collapsed navigation state is per-browser (localStorage), not server-side.

## Upgrade notes

* `Cargo.toml` is now `0.3.10`. Schema v9 contains data-only rule migrations.
* Existing rules that reference DET-22/24/25 still compile and remain visible,
  but those detectors no longer fire.
* DET-26 changes from alert-only to block-after-3 by default. Review/adjust the
  **Honeypot block after 3 contacts** rule if your policy differs.
* No menu URLs changed.
