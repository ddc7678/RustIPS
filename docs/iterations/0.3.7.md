# 0.3.7 — detector catalog and sidebar navigation

**Status:** implemented, post-RC UI/catalog release.
**Date:** 2026-11-21.

## Summary

0.3.7 makes the detection catalog visible and controllable from the UI and
moves primary navigation to a left sidebar:

* a **Detectors** page describes every detector, shows its live thresholds and
  path lists, and provides an enable/disable toggle;
* detector toggles are persisted in SQLite, apply without a restart, and are
  audited;
* navigation is now a left sidebar; the signed-in user, theme and logout remain
  in the top bar;
* `docs/detectors.md` explains detector vs disposition-rule layers and answers
  the custom-detection question.

No detector logic was changed; the 0.3.6 coverage result remains valid.

## What changed

### Detector catalog and detail view

`src/model.rs` gains:

* `DetectorCategory` (`packet`, `http`, `log`);
* `Detector::category()`;
* `Detector::description()` with a detailed "what it looks for" text for every
  detector.

`/detectors` shows:

* ID, title, category and enabled/disabled state;
* a Disable/Enable button per detector;
* "What it looks for" plus an expandable details block;
* **live configuration** from the effective config, including:
  * packet thresholds/windows (`scan_ports`, `sweep_hosts`, `stealth_packets`,
    `ack_packets`, `udp_ports`, `icmp_*`, `syn_*`, `conn_rate`, tarpit ports,
    SSH rate, slow-scan thresholds);
  * HTTP ports, unique-path/404 thresholds, the actual `http_bad_paths` and
    `http_login_paths`, anomaly and flood limits;
  * log thresholds/windows for DET-16/21/22/23/24/25;
  * default disposition policy (ladder vs alert-only).

This directly answers "what is the HTTP detector looking for?" — the page shows
the current bad-path list, login paths, ports and thresholds rather than a
generic description.

### Enable/disable detectors

* `settings.detection.disabled` stores the disabled detector IDs as a JSON
  array. Missing entries mean enabled.
* `Db::is_detector_disabled()` is checked at the top of the shared
  `record_detection` path, before evidence is stored. A disabled detector
  records nothing and cannot block.
* Existing blocks and strikes are **not** removed when a detector is disabled.
* The setting applies to the next detection without a restart.
* Toggles are audited as `detector.enable`/`detector.disable`.
* Suppressed detections increment `rustips_detections_suppressed_total` and
  `detections_suppressed` in `/api/summary`.
* There is no CLI enable/disable command yet; the Detectors page is the
  administrative path.

### Left sidebar navigation

`pages::shell` now renders:

```
+----------------+------------------------------------------+
| RustIPS 0.3.7  |                    user theme logout     |
| Dashboard      +------------------------------------------+
| Detections     | banners                                  |
| Detectors      | main content                             |
| Logs           |                                          |
| ...            |                                          |
| Settings       |                                          |
| Audit          | footer                                   |
+----------------+------------------------------------------+
```

* `.layout` is a flex row; `.sidebar` is 220 px, sticky/full-height with a
  vertical nav; `.content` holds the top bar, banners, main and footer.
* The top bar now contains only the signed-in user, theme toggle and logout,
  aligned right.
* At ≤820 px the sidebar becomes a horizontal/wrapping nav above the content
  and the top bar becomes static.
* The login page is unchanged (it is its own standalone page).

### Custom detection rules

The detection engine is modular internally but **not** a scriptable signature
engine. See `docs/detectors.md` for the full explanation:

* compiled packet/HTTP/log modules + a separate data-driven disposition engine;
* admins can enable/disable detectors, tune thresholds/paths, filter journal
  units/identifiers, and create disposition rules (including country/ASN);
* admins cannot create new detector logic or paste regex/scripts into the
  privileged path in 0.3.7;
* a future custom-detection feature would need a bounded linear-time matcher,
  length caps, validation/dry-run and a security review.

## Lab validation

On the 0.3.6 lab VM (upgraded to 0.3.7):

* `/detectors` shows all 23 detectors; DET-12 lists the configured bad paths
  and DET-11/13/15 show the HTTP ports/thresholds;
* disabling DET-12 through the UI persists `detection.disabled` and the page
  shows `disabled`; enabling restores it;
* the left sidebar renders on Dashboard/Detectors, and the top bar keeps the
  user/theme/logout controls;
* `rustips status`, `/readyz`, geo/journal/alerts are unchanged.

## Known limitations

1. Custom detection logic/signatures are not supported (compiled detectors only).
2. Enabling/disabling is global, not per-rule or per-target; disposition rules
   on the Rules page control action.
3. Disabling a detector is stored only in the local DB and is not included in
   export/import.
4. Historical detections remain visible after disabling a detector.
5. The sidebar is a server-rendered layout; there is no collapsible desktop
   mode/icon rail.

## Upgrade notes

* `Cargo.toml` is now `0.3.7`. No schema change (v7).
* No config change is required; all detectors start enabled as before.
* The Detectors page and left sidebar are UI-only additions.
* Disabling a detector is a local operational choice; use Rules for alert vs
  block policy.
