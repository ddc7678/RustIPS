# 0.3.12 — Active-blocks confirm-attribute fix

**Status:** bugfix release.
**Date:** 2026-11-21.

## Problem

The 0.3.11 clickable-IP change reused the same `{src}` placeholder for the
Active blocks source cell and the Unblock form's `data-confirm` attribute. The
cell correctly held the new `<button class="ip-link" …>` markup, but that markup
was also inserted inside:

```html
data-confirm="Unblock <button …>…</button>?"
```

which broke the attribute and rendered as:

```text
103.41.19.124?"> Unblock
```

## Fix

`pages::block_rows()` now uses separate values:

* `src = ip_link(block.src)` for the table cell;
* `src_text = esc(...)` for `data-confirm`;
* `src_raw = esc(...)` for the hidden form value.

No other page reused the clickable HTML inside an attribute; Detections already
built its block-confirmation text from a plain escaped address.

## Tests

* Web test creates a temporary block and asserts the Active blocks page contains
  `data-confirm="Unblock 203.0.113.99?"`, no nested button in the attribute, and
  a clickable `data-ip` source.
* Full suite: 158 tests pass (144 library, 6 CLI, 2 webhook, 1 replay,
  3 robustness, 1 scorecard, 1 web); clippy/fmt clean.

## Lab validation

Created a temporary block for a TEST-NET address, loaded `/blocks`, confirmed the
confirmation attribute and Unblock form were valid, then removed the block.
`blocks: 0 active` afterwards.
