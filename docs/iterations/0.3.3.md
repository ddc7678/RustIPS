# 0.3.3 — hardening, alerting and slow-scan detection

**Status:** implemented, pre-release (webhook alerting, DET-20, sample geo
rules, retention aggregation and robustness tests; optional eBPF/XDP and
file-log work remain later).
**Spec:** `requirements.md` revision 8, FR-204/204a/204b, FR-205, DET-20.
**Date:** 2026-11-21.

## Summary

0.3.3 adds the operational layer around the detection engine:

* **Generic webhook alerting** with a persisted, bounded, deduplicated queue,
  asynchronous delivery, bounded retries/backoff and health/metrics visibility.
* **DET-20 slow-scan detection**: unique destination ports accumulated over a
  long window while the short-window rate stays low.
* **Five disabled sample GeoIP/ASN rules**, loadable from the Rules page or
  `rustips rules samples`, so country/ASN examples are available without
  enabling a country policy by default.
* **Retention/aggregation improvements**: daily detection counts survive raw
  pruning; delivered/failed alert rows are pruned; daily
  `PRAGMA optimize`/WAL checkpoint.
* **Fuzz-like robustness tests** for decoders, the journal parser, the message
  sanitizer and the HTTP parser.

No new crates were added. Webhook delivery uses the system `curl` (already an
optional dependency for geo updates).

## What changed

### Webhook alerting (FR-204/204a/204b)

Webhook destinations are managed in the UI under **Alerts**: add, edit and
remove targets, each with its own URL, event filter, minimum severity, timeout,
retry count, dedupe window and queue cap. The `[alerts]` config section is now
only a one-time bootstrap and a global retention default:

```toml
[alerts]
enabled = false        # bootstrap only
url = ""               # if set on first start, seeds "Default webhook"
retention_days = 7     # default; the UI can override it
```

On the first start after upgrading, a non-empty `[alerts].url` creates a
"Default webhook" target from the other fields. After that the DB/UI is
authoritative; deleting all targets does not recreate them from the file.

`src/alerts.rs` and schema v6 add:

* `alert_targets` (name, enabled, URL, events, severity, timeout, retries,
  dedupe window, queue cap) managed by the Alerts page;
* `alert_queue` with state (`pending`/`delivered`/`failed`), target ID, attempts,
  `next_attempt_ms`, a unique dedupe key and the JSON payload;
* enqueue from the shared `record_detection` path for every disposition
  (`blocked`, `observed`, `dry_run`, `alert`, `allow`, `tag`, allowlisted and
  no-source outcomes);
* one queue row per enabled matching target, with per-target retries and
  dedupe; a dedicated delivery thread posts JSON with `curl` and a bounded
  timeout, never from the detection path;
* exponential backoff (5 s → 10 s → 20 s → 40 s → 80 s, capped at 300 s) up to
  `max_retries`; after that the row is marked failed and is not retried;
* dedupe by detector, source and action inside each target's rate window;
* per-target `queue_max` bounds pending rows by dropping the oldest;
* the UI retention setting (default from `alerts.retention_days`) prunes
  delivered/failed rows daily;
* operational alerts for geo update failures (`event: "operational"`);
* `/metrics` counters/gauges, `/api/summary` fields, Settings queue status,
  `rustips status` and a `rustips check` warning if `curl` is missing.

The payload contains detector/source/destination, count/window, action, rule
ID/name, matched rules, severity, country/ASN and timestamps. It does **not**
include raw log messages, request bodies or full metadata.

`scripts/webhook-email-bridge.py` is the documented SMTP bridge: a small
Python 3 HTTP server that accepts the webhook and sends e-mail through SMTP or
`sendmail`. It supports `--self-test`, `--dry-run` and `--once`.

### DET-20 slow scan

`Detector::SlowScan` is DET-20. On each inbound SYN the engine adds the
destination port to a per-source long-window set and evaluates:

* unique ports in `slow_scan_window_secs` (default 600) ≥ `slow_scan_ports`
  (default 30);
* ports in the shared 10-second window ≤ `slow_scan_max_per_window`
  (default 10), so a fast scan remains DET-01 rather than DET-20;
* the detector cooldown is `slow_scan_cooldown_secs` (default 600).

The default rule is **alert only**; an operator can add a block rule. This
keeps the false-positive cost of a long-window heuristic low. State is bounded
by the existing per-source cap and a 256-port slow-set cap.

### Sample country/ASN rules

`rules::sample_geo_rules()` returns five disabled examples:

| Name | Action | Match |
|---|---|---|
| Geo alert: China | alert | country CN |
| Geo block 24h: high-risk list | block 24h | CN, RU, KP, IR |
| Geo allow: partner ASNs | allow | ASN 13335, 15169 |
| Geo escalate: hosting ASNs | escalate 24h → 48h → permanent | ASN 16509, 14618, 8075 |
| Geo alert: outside expected countries | alert | not US, GB, DE, CA, AU |

The Rules page has a **Sample geo rules** panel and a load button; repeated
clicks do not duplicate a sample by name. `rustips rules samples` prints a
table, `--json` emits an importable `rustips-rules` document, and
`docs/examples/geo-rules.json` is the checked-in copy. Samples are added
disabled, preserving FR-138 (no country rule enabled by default). See
`docs/geo-rules.md`.

### Retention and aggregation

* `detection_daily(day, detector, count)` is updated before raw detections are
  pruned, so long-term daily counts survive the 30-day detection retention.
* Delivered/failed alert rows are pruned after `alerts.retention_days`.
* The daily maintenance pass runs `PRAGMA optimize` and
  `PRAGMA wal_checkpoint(TRUNCATE)`.
* The existing detection/block/audit/log retention paths are unchanged.

### Robustness

* `tests/robustness.rs`: 5,000 random inputs each for the packet decoders, the
  journal JSON parser and the message sanitizer; asserts bounded payloads,
  length caps and no control characters.
* HTTP parser fuzz test: 2,000 random payloads through request and response
  paths; asserts bounded flow/client tables.
* `tests/alerts.rs`: local endpoint returns 500 then 200; verifies retry,
  dedupe, delivered state across a database reopen, and permanent failure.

## Known limitations

1. Webhook delivery is **at-least-once**: a crash after the endpoint accepts a
   POST but before the local delivered mark can resend that event.
2. There is no HMAC/signature header and no per-endpoint TLS configuration;
   protect HTTP URLs, prefer HTTPS, and treat the URL as a secret.
3. Alert targets and per-target delivery settings are UI-managed; the config
   file only bootstraps a legacy default target and sets the initial retention
   default. Alert channels other than the webhook are out of scope.
4. FR-205 is partial: geo update failures emit operational alerts, but capture
   drop, journal stall, DB and nftables failures do not yet all do so.
5. DET-20 is alert-only by default and uses a long heuristic window; review it
   with `/rules/check` before adding a block rule.
6. The daily detection aggregate has no UI/API yet.
7. There is no coverage-guided fuzzer or multi-hour soak harness; the
   robustness suite is deterministic and bounded.
8. The optional eBPF/XDP capture path is deferred; AF_PACKET remains the only
   capture backend.
9. File log sources, rotation and DET-23 remain from the 0.3.0 theme.

## Upgrade notes

* `Cargo.toml` is now `0.3.3`. Schema v6 adds `alert_targets`,
  `alert_queue.target_id`, `alert_queue` and `detection_daily` (the v5 tables);
  a data migration adds the DET-20 "Slow scan alert" rule when no rule already
  references DET-20.
* `[alerts]` is a new optional section; old configs parse unchanged. A
  non-empty URL creates one disabled/enabled "Default webhook" target on first
  start; after that, manage targets on the Alerts page. Delivery requires
  `curl`.
* The `[detection]` slow-scan keys are optional and default to 30 ports /
  600 s / 10 recent ports / 600 s cooldown.
* The Rules page gains a sample geo panel; `rustips rules samples` is the CLI
  equivalent. Samples are disabled and do not change enforcement until enabled.
* No existing detector thresholds, rules or rule actions change on upgrade
  except the addition of the alert-only DET-20 rule.
