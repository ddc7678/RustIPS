# 0.3.8 — detector scope and editable parameters

**Status:** implemented, post-RC UI/configuration release.
**Date:** 2026-11-21.

## Summary

0.3.8 makes the detector catalog operational:

* every detector has an operator-facing **scope**: `external` (network traffic
  and authentication attempts from other hosts) or `internal` (local privileged
  activity on this host);
* every detector threshold, window and path/login list is **editable** from the
  Detectors page;
* values are validated and stored as overrides in SQLite, applied after the
  config file at daemon start;
* reset is available per field, per detector/shared group, and globally;
* the page shows the running value, the built-in default, a `modified` tag and
  the stored override that will apply after restart.

Detection logic itself is unchanged and remains compiled Rust.

## Scope

`src/model.rs` adds:

```rust
pub enum DetectorScope { External, Internal }

impl DetectorScope {
    pub fn as_str(self) -> &'static str;
    pub fn parse(value: &str) -> Option<Self>;
}

impl Detector {
    pub fn scope(self) -> DetectorScope;
}
```

Classification:

| Scope | Detectors | Count |
|---|---|---|
| external | DET-01…21, DET-23 (packet, HTTP, SSH/PAM/auth and access-log evidence) | 20 |
| internal | DET-22 sudo denial, DET-24 system security change, DET-25 account modification | 3 |

The Detectors page shows a Scope column, external/internal counts, and an
external/internal filter (`/detectors?scope=external|internal`).

Scope is independent of the transport category (`packet`/`http`/`log`); both
are displayed.

## Editable parameters

A new registry in `src/params.rs` is the single source of truth for editable
keys:

* `ParamSpec { key, label, kind, help }`;
* `ParamKind::Number { min, max }`, `Bool`, `PortList`, `TextList`;
* `SPECS` (all keys) and `keys_for(detector-or-shared-group)`;
* `value(&Config, key)` / `default_value(key)` via a typed TOML round-trip;
* `normalize(spec, raw)` — trims, range-checks, parses ports, deduplicates list
  items, rejects control characters and over-long items;
* `apply_overrides(&mut Config, map)` — sets TOML paths on the serialized
  config, deserializes a complete `Config`, then calls `Config::validate`.

Editable groups:

| Group | Keys |
|---|---|
| shared packet | `window_secs`, `cooldown_secs`, `max_tracked_sources` |
| shared HTTP | `http_ports` (used by DET-11…15) |
| shared log | `logs.detection.window_secs`, `cooldown_secs`, `max_tracked_sources` |
| DET-01…10 | packet thresholds/windows/lists |
| DET-11 | HTTP unique-path/404 thresholds and scan window |
| DET-12 | `http_bad_paths` |
| DET-13 | auth threshold/window and `http_login_paths` |
| DET-14 | anomaly threshold/window |
| DET-15 | flood threshold/window |
| DET-16/21/22 | log failure thresholds (plus shared log window) |
| DET-20 | slow-scan thresholds/windows |
| DET-23 | log-side path/404 thresholds and window |
| DET-24/25 | enable-security/account-change booleans |
| DET-17 | none (event condition only) |

`http_ports` is intentionally edited once in the shared HTTP panel instead of
in each HTTP detector, because it is shared by DET-11…15.

## Storage and application

* Overrides live in `settings.detection.overrides` as a JSON object of
  `key → string`.
* `Db::detection_overrides()`, `set_detection_overrides(changes, remove)`,
  `clear_detection_overrides(keys)` and `clear_all_detection_overrides()`.
* Saving a value equal to the running configuration leaves that key unchanged;
  any different value is stored as an override (including a value that happens
  to equal the built-in default, when the config file customised it).
* Reset removes the override, so the configuration file value applies.
* `cli::load_config` applies stored overrides after loading `config.toml` and
  before the daemon starts; the merged `Config` is validated.
* `check` prints `overrides: N applied` or `overrides: none stored`; an invalid
  override is a hard check failure.
* `diagnose` prints the stored/applied override count.
* Parameter changes require a restart. Detector enable/disable still applies
  live.
* Overrides are local state, not written back to `config.toml`, and are not
  part of rules/block export/import.

## Web routes

| Route | Action |
|---|---|
| `GET /detectors?scope=external\|internal` | scoped catalog |
| `POST /detectors/toggle` | enable/disable (unchanged) |
| `POST /detectors/params` with `action=save` | validate and store the submitted group |
| `POST /detectors/params` with `reset_key=KEY` | remove one override |
| `POST /detectors/params` with `action=reset_scope` | remove the group's overrides |
| `POST /detectors/params` with `action=reset_all` | remove every override |

All actions use the authenticated, CSRF-protected POST path and are audited as
`detection.params.save` / `detection.params.reset`.

Each field has its own **Reset to default** button (a named submit inside the
group form), so reset does not require a separate request or page.

## Validation and failure behaviour

* Numbers are rejected outside their configured min/max.
* Ports must parse as 1–65535; blank items are ignored; duplicates removed.
* Text-list items are limited to 256 characters and cannot contain control
  characters.
* Unknown parameter keys and unknown groups are rejected with HTTP 400.
* Invalid submissions leave stored overrides unchanged.
* Invalid stored overrides fail `rustips check` and daemon start with a clear
  `stored detection overrides: …` error rather than silently running defaults.

* `/detectors` shows 20 external and 3 internal detectors and the filter works;
* DET-12 `http_bad_paths` was edited through the UI, persisted in
  `detection.overrides`, shown as modified, and applied after restart;

* `rustips check` reported the stored override; `/readyz` and existing rules,
  geo and alerts were unaffected.

## Known limitations

1. Detection logic is still compiled Rust; administrators can tune and
   enable/disable detectors but cannot create new detection signatures in 0.3.x.
2. Overrides are global, not per-rule or per-target; disposition remains on the
   Rules page.
3. Overrides are not exported/imported and are not written to `config.toml`.
4. Parameter changes require a restart; the page states this and previews the
   pending value.
5. The field reset button submits the enclosing group form, so values typed in
   other fields in the same group are discarded when resetting one field.

## Upgrade notes

* `Cargo.toml` is now `0.3.8`. No schema change (v7).
* No config change is required; all detectors start with the configured values.
* Existing `detection.disabled` state is unaffected.
* Existing deployments can begin editing parameters immediately; restart to
  apply the override.
