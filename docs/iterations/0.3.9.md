# 0.3.9 — navigation, flash-free theme and honeypot

**Status:** implemented, post-RC UI/feature release.
**Date:** 2026-11-21.

## Summary

0.3.9 cleans up the admin experience and adds an optional network honeypot:

* sidebar navigation is grouped by function;
* the Rules menu item is now **Disposition rules**;
* the version moves from the sidebar brand and page footer into the sidebar
  footer (`RustIPS: <version>`), and “bound to” is removed;
* the saved theme is applied before the page paints, so navigation no longer
  flashes light mode;
* an optional **honeypot** watches unused TCP/UDP ports and emits DET-26. It is
  disabled by default and configured in Settings.

The sidebar is now:

## Flash-free theme

Previously `app.js` (loaded with `defer`) read `localStorage` after the page had
already started rendering, so a dark-theme user could briefly see light mode.

Now:

* `/assets/theme.js` is a tiny synchronous script included in `<head>` **before**
  the stylesheet;
* it reads `rustips-theme` and sets `document.documentElement.dataset.theme`
  before the body paints;
* `app.js` still owns the theme toggle and writes the same key;
* the login page and error pages also include `theme.js`;
* the CSP remains `script-src 'self'` — no inline script was added.

## Honeypot (DET-26)

### Behaviour

* Disabled by default (`detection.honeypot_enabled = false`,
  `detection.honeypot_ports = []`).
* Any inbound TCP SYN or UDP datagram from another host to a configured
  honeypot port emits DET-26.
* No listener is required; the packet sensor sees the attempt.
* A source emits at most one honeypot detection per detector cooldown, even if
  it probes several honeypot ports.
* DET-26 is **alert-only by default**, so it falls through to the shipped
  catch-all alert rule. An administrator can add a Disposition rule to block or
  escalate it.
* The detector can also be disabled with the normal Detectors toggle.

### Configuration and UI

New `Detection` fields:

```toml
[detection]
honeypot_enabled = false
honeypot_ports = []
```

Validation:

* ports must be 1–65535 (the Settings/Detectors form normalizes and
  deduplicates);
* enabling the honeypot with an empty port list is rejected by `Config::validate`
  and by the web save path before anything is stored.

The Settings page has a **Honeypot** panel using the existing detection
parameter override machinery (`scope=honeypot`):

* enable checkbox;
* comma-separated port list;
* per-field reset, group reset and the standard restart notice.

The DET-26 catalog row shows `honeypot_enabled` and the live port list and lets
an administrator edit the ports; the feature switch is in Settings.

### Detection path

`Engine::observe` checks the honeypot before the normal per-protocol detector
match:

```text
inbound packet to a local address
  honeypot enabled?
    TCP SYN (not SYN/ACK) or UDP datagram
      destination port in honeypot_ports?
        emit DET-26 (cooldown per source)
```

Metadata includes `port`, `protocol` and `honeypot: true`.

## Known limitations

1. Honeypot detection is TCP SYN / UDP datagram based; a mid-stream connection
   whose SYN was not captured is not detected.
2. A source is alerted once per cooldown, not once per honeypot port.
3. DET-26 is alert-only by default; blocking needs an explicit Disposition rule.
4. Honeypot changes require a daemon restart.
5. The honeypot does not open or emulate services; it relies on the packet
   sensor observing attempts to ports that are otherwise closed.

## Upgrade notes

* The honeypot is off until enabled in Settings.
