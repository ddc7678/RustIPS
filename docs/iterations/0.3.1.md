# 0.3.1 — disposition rules platform

**Status:** implemented, pre-release (rules engine, storage, UI/CLI and
import/export; GeoIP country/ASN conditions arrive with 0.3.2).
**Spec:** `requirements.md` revision 8, §6.3.
**Date:** 2026-11-20.

## Summary

0.3.1 turns detection disposition into data. Every detection is evaluated
against an ordered set of rules stored in SQLite; matching rules accumulate and
combine into one action. The hard-coded 0.3.0 policy is shipped as four default
rules, so an upgrade changes no blocking behaviour until an administrator edits
or imports a rule.

Rules support validation, revision history, dry-run, import/export and a UI
editor. Changes are picked up by the daemon within about a second; a rejected
reload keeps the last-good set, so a mistake cannot leave the host without
rules.

No new crates were added. The rules are serialised with the existing `serde` /
`serde_json` dependency and stored in the existing SQLite database.

## What changed

### Rule model and evaluation (FR-120…125)

A rule has a stable ID, name, description, enabled/dry-run flags, priority,
severity, match conditions and one action. The persisted JSON is the source of
truth; IDs are assigned on first save and never reused for a new rule.

Match conditions available in 0.3.1:

* detector IDs (`DET-01`…`DET-25`; empty = any);
* source CIDRs and exclude CIDRs (empty = any);
* destination port or ranges (`22`, `8000-8100`);
* protocol (`tcp`, `udp`, `icmp`, `icmp6`, `log`);
* minimum detection count;
* minimum source strike count;
* currently blocked;
* last strike within a duration;
* metadata tags;
* UTC weekday set and an optional `HH:MM` window (wraps midnight).

Actions:

| Action | Behaviour |
|---|---|
| `alert` | record and audit, never block |
| `tag` | annotate the detection metadata |
| `allow` | exempt the source from blocking |
| `block_temp` | fixed duration, e.g. `1h` |
| `block_permanent` | permanent block |
| `escalate` | use the global ladder, or a per-rule ladder override |

Evaluation is **accumulating**, not first-match (FR-121). All enabled matching
rules are collected, then actions combine (FR-123):

1. any `allow` wins;
2. otherwise the longest block wins (permanent absorbs temporary blocks);
3. otherwise `alert` wins over `tag`;
4. tags from every matching tag rule are still applied.

Ties break on severity (critical > warning > info), then rule priority (higher
first), then the lowest rule ID. The matched IDs, the winner and the resolved
action are recorded in the audit detail; a block also stores `rule_id`
(FR-122).

A `dry_run` rule records the intended action as `rule.dry_run` and never strikes
or enforces. Global observe mode still wins over every rule (FR-125).

### Defaults (FR-128)

Four rules are seeded when the schema is created or migrated:

| ID | Name | Match | Action |
|---|---|---|---|
| 1 | Log authentication failures | DET-16/21/22 | escalate (global ladder) |
| 2 | Log alert-only detections | DET-17/24/25 | alert |
| 3 | Packet detections escalate | DET-01…10 | escalate (global ladder) |
| 4 | Default alert | any detection | alert |

These reproduce 0.3.0 exactly. New detectors fall through to the catch-all
alert until an operator adds a rule, which is the safe default.

### Storage and history (FR-120, FR-126)

Schema v3 adds:

* `rules`: the current document plus name/enabled/priority/severity/revision
  columns for ordering and filtering;
* `rule_revisions`: one immutable row per create/update/delete/import with the
  actor, note, timestamp and full document;
* `rules_meta`: the rule-set version used by the daemon to notice changes;
* `blocks.rule_id`: the winning rule on a block.

v1/v2 databases migrate in place. Deleting or disabling the last enabled rule
is refused. On startup or reload, the rule set is compiled and validated; an
unreadable or invalid set logs `rules.load_failed`, audits the errors and keeps
the previous in-memory set (or the shipped defaults at startup).

### UI and CLI

* `/rules`: list, create, edit, delete, revision history, import/export and a
  dry-run view over the last 100 detections.
* `/rules/check`: evaluates the stored rules against recent detections with
  their current strike/block history. It writes nothing and enforces nothing.
* `/rules/export` returns a JSON document; the import form accepts that document
  or a bare JSON array, validates the whole set and replaces the stored rules.
* `rustips rules check`, `rustips rules list`; `rustips check` validates the
  rules; `rustips status` shows the stored rule count.
* `rustips export` includes rules (export version 2); `rustips import`
  validates before replacing them. Old exports without rules leave the current
  set untouched.

Every rule save/delete/import is audited with the admin actor. Every disposition
audit line includes `rules=<ids> winner=<id> (<name>)`.

### Operational behaviour

The packet and journal paths call the shared `record_detection`, which now:

1. stores the detection;
2. gathers strike/block history;
3. evaluates the shared rule set under a read lock;
4. merges tags into the detection;
5. rejects no-source detections and allowlisted/implicit sources from blocking;
6. applies allow/alert/tag, dry-run/observe, or the strike ladder and
   enforcement with the winning duration and rule ID.

The scheduler polls the rule-set version every 500 ms and swaps in a compiled
set after a successful reload.

## Lab validation

On the Debian 13 QEMU guest, upgrading the existing 0.3.0 installation:

| Check | Result |
|---|---|
| Schema upgrade | v2 → v3 in place; existing detections, log events and blocks preserved |
| Defaults | `rustips rules list` shows 4 rules matching the 0.3.0 policy |
| `rustips check` | `rules: OK (4 rules)`, overall `result: OK` |
| UI list/edit | `/rules` rendered; a 3-hour `block_temp` rule for DET-21 saved |
| Hot reload | daemon logged `rules reloaded version=2` within a second |
| Evaluation | 5 synthetic `pam_unix(dovecot:auth)` failures → `rules=5,1,4 winner=5 (VM test rule) duration=3h escalated=false`, observe mode |
| Cleanup | deleting the rule restored the four defaults |
| Status | `rustips status` shows `rules: 4 stored`; journal ingestion still running |

The first 0.3.1 deploy attempt exposed an upgrade race: `rustips status` opened
the database read-only before the new daemon had migrated it, saw schema v2 and
failed verification. `status`/`export`/`allowlist`/`detections` now open the
database read/write so the migration runs before their first query; the second
deploy completed and verified.

## Known limitations

1. GeoIP/ASN conditions are not in the rule schema yet; they arrive in 0.3.2.
2. HTTP path/status conditions and DET-11…15 are 0.3.2.
3. `alert_channels` and webhook delivery are 0.3.3.
4. YAML rules are not supported; JSON is the import/export format.
5. Rule editing covers rules only; `[detection]`, `[ladder]` and `[logs]`
   configuration remain file-driven.
6. Rule reload compares a database version counter; it does not watch the file
   system. Every supported edit path (UI, CLI import, `replace_rules`) bumps it.
7. `keep-but-decay` unblock semantics remain unimplemented.
8. A rule can match on metadata tags, but no detector emits tags by default;
   `tag` actions are the current producer.
9. File log sources, rotation and DET-23 (FR-319…335) remain from the 0.3.0
   host-log theme. Rules apply to journal and file detections alike once file
   sources land.

## Upgrade notes

* `Cargo.toml` is now `0.3.1`. Schema v3 migrates a v1/v2 database in place and
  seeds the four defaults. Back up `/var/lib/rustips/rustips.db` as usual.
* No configuration file change is required. Existing `[ladder]` and
  `[detection]` settings continue to apply; `escalate` rules without an
  override use `[ladder].steps`.
* The UI gets a **Rules** navigation entry. `rustips check` now reports rule
  validity. `rustips export` format version 2 adds `rules`; old export files
  still import, leaving the current rules untouched.
* Because the default rules reproduce 0.3.0, an upgrade with no rule edits
  produces the same dispositions as before.
