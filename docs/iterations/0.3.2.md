# 0.3.2 — GeoIP/ASN enrichment and packet HTTP detectors

**Status:** implemented, pre-release (disposition-only geo data and packet HTTP
detectors; file sources, DET-23 and webhooks remain later work).
**Spec:** `requirements.md` revision 8, §6.2.2 and FR-160…169.
**Date:** 2026-11-20.

## Summary

0.3.2 adds two independent capabilities:

1. **Disposition-only GeoIP/ASN enrichment.** `rustips geo update` downloads
   the `user-country` and `origin-asn` CSV releases, verifies the published
   SHA-256 checksums, builds compact sorted range indexes, and hot-swaps them
   into the daemon. Rules can match country and ASN, but only after a real
   detection; geo data never creates one.
2. **Packet HTTP detectors DET-11…15.** Clear-text requests on configured ports
   are parsed for path scans, known-bad paths, login brute force, method/Host
   anomalies and request floods. Responses are correlated to requests so
   404/401/403 outcomes can be scored.

No new crates were added. Downloads use the system `curl`; TLS is not linked
into the binary.

## What changed

### Geo index format and building

`src/geo/mod.rs` defines a compact binary format:

* 20-byte header (`RIPSGEO1`, kind, value width, v4/v6 counts);
* country records: 10 bytes per v4 range and 34 bytes per v6 range;
* ASN records: 12 bytes per v4 range and 36 bytes per v6 range;
* records are sorted by start address and validated for non-overlap at build
  time; a malformed or overlapping CSV is rejected before install.

Lookup is a binary search over the byte buffer, with no per-query allocation.
The real datasets measured:

| Index | IPv4 records | IPv6 records | Size |
|---|---:|---:|---:|
| country | 302,722 | 295,102 | 13.1 MB |
| ASN | 447,366 | 128,657 | 10.0 MB |
| **total** | | | **23.1 MB** |

That is under the FR-162 25 MB budget. Building both indexes from local CSVs
takes about 0.3 s.

The downloaded CSVs are verified against the release `.sha256` files with a
small pure-Rust SHA-256 implementation (tested against the standard empty and
`abc` vectors). A failed download, checksum or build leaves the live indexes
untouched. Installation renames the new file into place and keeps the previous
generation as `.prev` (FR-164).

### Update path and hot swap

`src/geo/update.rs` implements:

* four downloads (`country`/`asn` × `ipv4`/`ipv6`) and their checksums using
  `curl --fail --location --max-time 180 --max-filesize 64M`;
* build → install → remove the temporary directory;
* a background updater that runs every `geo.update_hours` (default 24 h),
  honours a manual `geo.request` setting from the UI, and reloads CLI-installed
  indexes via `geo.reload`;
* a `geo.status` setting containing last check/success/next check, last error,
  and per-index generation, SHA-256, record counts, size and load time.

The daemon holds `Arc<RwLock<GeoData>>`. A successful update/rebuild swaps the
`Arc<GeoIndex>` values under the write lock, so rule evaluation sees either the
old or the new generation, never a partial file (FR-165).

The update is off by default (`[geo].enabled = false`) so a fresh install makes
no external requests. A manual update still works while automatic updates are
disabled.

### Geo rule conditions (FR-137…139)

`RuleMatch` gains:

* `countries` / `not_countries` (two-letter ISO codes);
* `asns` / `not_asns` (32-bit ASNs, `AS` prefix accepted).

The conditions require the corresponding index and a non-empty lookup. If no
index is loaded, a rule with geo conditions simply does not match (FR-167), and
the Rules page says "not configured". The engine never consults geo for
detection; `record_detection` looks up the source only after a detection exists
and passes a `GeoInfo` into the rule evaluator.

The rule editor exposes the fields, the list shows `country CN` / `asn 64500`,
and the rule-check view evaluates historical detections with the current
indexes.

### Packet HTTP detectors DET-11…15

`src/detect/http.rs` adds a bounded HTTP engine. It is only active on
`detection.http_ports` (default 80, 8080, 8000, 8888) and only for TCP.

Request side:

* one complete request head per flow is buffered (2 KB cap, FR-117), parsed for method,
  target, version and Host;
* DET-12 fires immediately on a configured bad-path substring;
* DET-11 fires at 20 unique paths in 30 s;
* DET-14 fires at 3 method/request-line/Host anomalies in 60 s (TRACE/unknown
  methods, malformed line, missing Host on HTTP/1.1, suspicious Host, path
  traversal);
* DET-15 fires at 100 requests in 10 s per source.

Response side:

* status lines are parsed on the reverse tuple and correlated to the request;
* DET-11 also fires at 15 404/403 responses in 30 s;
* DET-13 fires at 10 401/403 responses on login-ish paths in 60 s.

Flow buffers expire after 30 s; flows and clients are capped and pruned. One
request per connection is counted, so a keep-alive burst on a single connection
may undercount DET-15; the limitation is recorded in the detection metadata and
docs. DET-15 identifies the burst and the ladder blocks; there is no separate
kernel rate-limit stage yet.

Detection rows carry method/path/host/status/count evidence, and the existing
rule pipeline applies the configured action. The shipped packet rule includes
DET-11…15 for fresh installs; an existing 0.3.1 database gets a one-time
"HTTP detectors escalate" rule via schema v4 unless a rule already mentions
any HTTP detector.

### Storage and migration

Schema v4 is a data-only migration: it adds the HTTP rule where needed. No new
tables; geo status and generation metadata live in the existing `settings`
table. The geo indexes live under `<state>/geo/`.

## Known limitations

1. FR-163 conditional requests: the updater uses a 24 h cadence and checksums,
   not ETag/Last-Modified. A check still fetches the four small checksum files,
   but skips the ~30 MB of CSV downloads when nothing changed.
2. DET-15 fires and the rule ladder blocks; a separate kernel rate-limit stage
   before blocking is not implemented.
3. HTTP parsing counts one request per connection. Keep-alive/pipelined bursts
   may undercount DET-11/15.
4. HTTPS is not inspected (no TLS interception).
5. File log sources, rotation, DET-23 and the dedicated mail/HTTP/syslog
   parsers remain deferred from the 0.3.0 theme.
6. Geo file upload through the browser is not implemented; use
   `rustips geo update --country-v4 …` on an air-gapped host.
7. Geo index lookups run on every detection; at normal detection rates this is
   negligible, but it is not cached per source.
8. The rules UI edits rules only; HTTP thresholds/path lists and `[geo]` URLs
   remain file-driven.

## Upgrade notes

* `Cargo.toml` is now `0.3.2`. Schema v4 adds the one-time HTTP rule.
* `[geo]` and the HTTP fields in `[detection]` are optional; old config files
  parse unchanged and receive the documented defaults. Geo is disabled by
  default.
* A fresh install includes DET-11…15 in the shipped packet-escalation rule. An
  existing 0.3.1 install gets a separate "HTTP detectors escalate" rule.
* Run `rustips geo update` (or the four local CSV options) before using
  country/ASN conditions. `rustips geo status` and the Rules page show whether
  an index is loaded.
* The UI has no new top-level page; geo status and "Check now" live under
  **Rules**.
